# kickoff — 프로젝트 시작 워크플로 (spec → plan → design-brief)

새 프로젝트/기능을 시작할 때 따르는 3단계 절차를 정의한다. 모든 AI 코딩 에이전트가 읽을 수 있는 **도구 중립 지침**이다. (Claude Code는 추가로 `SKILL.md`를 통해 `/kickoff` 슬래시 명령으로도 이 절차를 부른다.)

```
요구사항 정리 → ① spec.md → ② plan.md → ③ design-brief.md → (디자인 AI가 화면 제작)
```

**언제 적용하나:** 사용자가 새 프로젝트를 시작하거나, "프로젝트 시작하자 / spec 만들자 / plan 짜자 / MVP 단위로 계획 / 디자인 브리프 만들어" 같이 요청하거나, 만들 것의 목표·요구사항을 설명하며 구체화를 부탁할 때. 기존 `plan.md` 갱신(MVP 체크, 진행 기록 append)에도 쓴다.

이건 단순 문서 생성기가 아니다. 핵심은 **각 단계의 일하는 방식**이다 — spec은 쓰기 전에 검토 대화부터, plan은 검증 가능한 MVP 슬라이스, brief는 디자인 AI에게 넘길 깨끗한 입력. 이 방식이 곧 워크플로의 본질이라, 형식보다 이걸 지키는 게 중요하다.

**대화는 한국어로.** 생성하는 문서는 **한글 본문 + 영어 라벨/경로/코드** 혼용.

---

## 작동 방식 — 상태를 보고 단계를 정한다

### 0. 먼저 프로젝트 디렉토리를 확정한다 (스캔보다 먼저)

이건 *프로젝트 시작* 절차라, 첫 호출 때 작업 위치가 모호한 경우가 흔하다. 무엇이든 감지·생성하기 **전에** 프로젝트 루트부터 확정해라:

- **새 프로젝트**: 폴더가 아직 없으면 이름을 정하고 만든다(또는 만들 위치를 사용자와 확인). 이후 모든 문서는 그 폴더에 쓴다.
- **현재 위치가 컨테이너면 주의**: 사용자가 수십 개 프로젝트를 담는 상위 폴더에 있을 수 있다. 그곳을 프로젝트 루트로 착각하면 *다른* 프로젝트의 `SPEC.md`를 잘못 매칭해 단계를 오판하거나 헛된 "이미 있는데?" 확인을 띄운다. 한 폴더에 여러 프로젝트가 섞여 보이면, 어느 폴더가 이번 프로젝트인지 확인하고 거기로 좁힌다.
- **스캔 범위는 확정된 프로젝트 루트 안으로 한정.** 상위로 거슬러 올라가지 말고, 옆 프로젝트로 새지 마라.

### 그다음 — 단계 판단 (명시적 캐스케이드)

확정된 프로젝트 루트를 보고 **다음에 할 단계**를 정한다. 겹치지 않게 위에서부터 순서대로 판단한다:

1. **spec 없음** → **STAGE 1 (spec)**
2. **spec 있음 + plan 없음** → **STAGE 2 (plan)**
3. **spec 있음 + plan 있음 + brief 없음** → **STAGE 3 (brief)**
4. **셋 다 있음** → 생성할 게 없다. 현재 상태를 요약하고, 살아있는 plan.md 동기화(체크/진행기록 갱신)를 제안한다.

사용자가 특정 단계를 지정하면(예: "plan 짜자", `/kickoff brief`) 그 단계로 바로 간다. **brief는 spec에만 의존한다** — plan이 없어도 spec만 있으면 brief를 만들 수 있다. brief를 plan 뒤로 막지 마라.

### 캐노니컬 파일과 변형 감지 (덮어쓰기 사고 방지)

새로 만들 때의 표준 파일명·위치는 프로젝트 루트의 `spec.md`, `plan.md`, `design-brief.md`(화면 묶음이 여럿이면 surface별 복수 허용: `design-brief-app.md`, `design-brief-landing.md`).

**단, 감지는 정확매칭으로 하지 마라.** 기존 프로젝트는 파일명이 제각각이다 — `SPEC.md`, `CMS_Spec.md`, `TechSpec.md`, `DESIGN_BRIEF.md`, `landing-brief.md` 등. 단계를 정하기 전에 루트(필요하면 `docs/`, `documents/`도)에서 **대소문자 무시 + 부분 매칭**으로 이미 존재하는 파일을 먼저 찾아라:

- 이름에 `spec`이 든 `.md` → spec으로 간주
- 이름에 `plan`이 든 `.md` → plan으로 간주
- 이름에 `brief`가 든 `.md` → brief로 간주

변형 파일이 발견되면 **새로 만들지 말고**, "이미 `CMS_Spec.md`가 있는데 이어서 작업할까, 새 `spec.md`로 갈까?"처럼 확인하고 그 파일 위에서 작업해라. 기존 문서를 말없이 덮어쓰는 건 최악의 실패다.

## STAGE 1 — spec.md (가장 중요: 쓰기 전에 대화부터)

> **이 절차의 1번 실패 모드는, 검토 대화를 건너뛰고 곧장 spec.md를 써버리는 것이다.** spec.md를 만드는 건 대화의 *끝*이지 시작이 아니다.

1. **요구사항 청취.** 사용자가 목표·제약·아이디어를 설명한다. 이미 설명했다면 그걸 받는다.
2. **검토 먼저 — 여기서 가치를 낸다.** 바로 문서로 받아적지 말고, 능동적으로 제안해라:
   - 빠진 결정 사항 / 모호한 지점 (Open Questions)
   - 리스크, 함정, 약관·법적·기술적 제약
   - 더 단순한 대안, 스코프를 줄일 여지 (오버킬 경계)
   - 놓친 기회나 아이디어
   - **비목표(non-goals)** 후보 — 이번에 안 할 것을 같이 못박으면 스코프가 선명해진다
3. **합의.** 위 항목을 사용자와 주고받으며 좁힌다. 한 번에 다 답 안 나와도 된다 — 남는 건 Open Questions로 남긴다.
4. **그제서야 spec.md 작성.** 합의된 내용으로 `references/spec-template.md` 구조를 채운다.
5. **멈춘다.** spec을 보여주고, 충분히 검토·수정한 뒤 다음 단계(plan)로 가자고 안내한다. **자동으로 plan으로 넘어가지 마라.** spec은 사용자가 곱씹고 고치는 시간이 필요한 문서다.

---

## STAGE 2 — plan.md (검증 가능한 MVP 슬라이스, 살아있는 문서)

spec을 바탕으로 구현 계획을 MVP 단위로 쪼갠다. 핵심 원칙:

- **각 MVP는 그 자체로 동작·검증 가능한 슬라이스다.** 끝나면 데모 가능한 상태. "프론트 절반 + 백 절반" 같은 세로로 안 잘린 조각은 금물.
- **검증 책임을 🤖/🧑로 나눈다:**
  - 🤖 = 에이전트가 자동 검증 가능한 것 — 단위 테스트, 빌드 통과, 정적 검사, screenshot/eval 등 deterministic한 것
  - 🧑 = 사람만 판단할 것 — 미감, 실기기 동작, 모션 부드러움, 사용성 체감
  - 둘을 섞지 마라. 자동 게이트는 deterministic한 것만.
- **완료 게이트(🚪).** 다음 MVP로 넘어가려면 통과해야 하는 조건을 명시.
- **살아있는 문서.** 작업이 진행되면 체크박스를 채우고 "진행 기록"(섹션명은 이걸로 통일 — Changelog·작업 로그 등 변형 금지, **최신이 위**)에 새 줄을 넣는다. 진행 기록에는 **결정·이유·함정·되돌린 것만** — "MVP-N 완료" 류 상태 변경은 개요 표와 체크박스가 이미 말하므로 중복 금지.
- **자라기만 하는 문서는 금물 — 접는다.** plan.md는 세션마다 통째로 읽히므로 길이가 곧 토큰 비용이다. 완료 게이트가 닫힌 MVP는 본문에 3~5줄 요약(무엇이 동작하게 됐나 + 이후에도 유효한 함정·제약)만 남기고 상세(작업·검증·실제 결과 전문)를 문서 끝 "## 아카이브"로 내린다 — 삭제가 아니라 이동. 닫힌 MVP에 후속 작업이 생기면 그 밑에 즉흥 소제목을 붙이지 말고 새 MVP(또는 하드닝 H-트랙)로 올린다. 파일이 40KB를 넘으면 아카이브 섹션을 `plan-archive.md`로 분리하고 링크만 남긴다 — plan.md 하나만 읽으면 현재 상태가 파악되는 크기를 유지한다.

### plan이 이미 있으면 — 생성이 아니라 동기화

plan.md가 이미 있으면 **절대 통째로 덮어쓰지 마라.** 완료된 작업 체크박스를 채우고, 각 MVP의 "실제 결과"를 채우고, "진행 기록"에 새 줄을 prepend하고, spec이 바뀌었으면 영향받는 MVP만 조정한다. 닫힌 지 오래된 MVP가 상세를 그대로 이고 있으면 위의 접기 규칙을 적용한다(내용은 아카이브로 이동, 유실 금지).

구조는 `references/plan-template.md` 참고.

---

## STAGE 3 — design-brief.md (디자인 AI에게 넘길 입력)

사용자는 **spec + design-brief 두 문서를 디자인 AI에게 줘서 화면을 제작**한다. 따라서 brief는 "사람이 읽는 기획서"가 아니라 **디자인 AI가 받아먹기 좋은 입력**이다.

- **brief는 spec의 연장이다 — 중복하지 마라.** 동작/로직/인터랙션 규칙은 spec의 몫이다. brief는 **"어떻게 보일지(look & feel)"**를 다룬다. 겹치는 주제는 "spec 참고"로 cross-ref만.
- **산출물 형식을 못박아라.** 받을 결과가 Figma / HTML / SVG / PNG / 토큰 JSON 중 무엇인지 구체적으로.
- **❌ 하지 말 것 리스트를 반드시 넣어라.** 새 팔레트 임의 정의 금지, 스코프 밖 화면 금지 등.
- **화면 인벤토리.** 페이지/컴포넌트 목록 + 각 목적 + 우선순위.
- 화면 묶음이 성격이 다르면(앱 본체 vs 랜딩) brief를 surface별로 나눈다.

구조는 `references/brief-template.md` 참고.

---

## 공통 원칙

- **단계마다 멈춰서 사용자 검토를 받는다.** 한 번에 spec→plan→brief를 몰아서 뽑지 마라.
- **문서 경계를 넘지 마라.** spec=무엇/왜, plan=어떻게/언제/검증, brief=어떻게 보일지. 같은 내용을 세 곳에 적지 말고 cross-ref.
- **한글 본문 + 영어 라벨/경로/코드.** 명령조(`~한다`, `~해야 함`). 상태 이모지 `✅🟡🔴⬜` 일관 사용. 진행은 체크박스로.
- 템플릿(`references/*.md`)은 출발점일 뿐이다. 프로젝트 성격에 안 맞는 섹션은 빼고, 필요한 건 더해라.
