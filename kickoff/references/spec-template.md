# [프로젝트명] Spec

> **한 줄 정의.** 이 제품이 무엇이고 누구의 무엇을 해결하는지 한 문장으로.

## 1. 배경 / 문제
- 왜 만드는가. 지금 무엇이 불편한가.

## 2. 차별점 / 비목표
- **차별점**: 기존/대안 대비 무엇이 다른가.
- **비목표 (non-goals)**: 이번에 **안 할 것**. 스코프 경계를 여기서 못박는다.

## 3. 타겟 / 핵심 시나리오
- 주 사용자와 사용 맥락.
- 핵심 시나리오 1~3개 (사용자가 무엇을 하려고 들어와서 무엇을 얻고 나가는가).

## 4. 기술 스택
- 플랫폼(web/desktop/mobile), 프레임워크, 주요 라이브러리. 선택 이유 한 줄씩.

## 5. 데이터 / 입력 소스
- 어떤 데이터를 어디서 읽고/쓰는가. API, 파일, 외부 서비스, 권한.

## 6. 기능 / 시스템
- 핵심 기능을 시스템 단위로 기술. 규칙·상태·엣지케이스·폴백.
- (행동/로직의 정본은 여기. brief에서 중복하지 않는다.)

## 7. 아키텍처
- 컴포넌트 구성과 데이터 흐름. 필요하면 간단한 다이어그램/코드블록.

## 8. UI / 화면 구성
- 화면 목록과 각 역할 (상세 비주얼은 design-brief로 넘긴다).

## 9. 플랫폼 · 보안
- 배포 대상, 네트워크 전제, 인증, 민감정보 취급, 약관/정책 안전선.

## 10. 라이선스 / 리스크
- 라이선스, 의존성 리스크, 알려진 함정.

## 11. Open Questions
- 아직 결정 못 한 것. 검토 대화에서 남은 미해결 항목을 솔직하게 적는다.
